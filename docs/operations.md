# SYROTP Operations

Operator runbook for a production SYROTP deployment. Walks you from
"server is up" through "the dashboard is reachable, both gateway types
forward SMS, alerts fire when something breaks, and on-call knows what
to do when they fire."

If you're new here, run [Quickstart](../README.md#-path-1--quickstart-5-minutes)
first to get a local instance going. This page assumes that worked.

## 1. Metrics endpoint

SYROTP exposes Prometheus exposition at **`GET /metrics`** with no auth —
operators terminate access at the reverse proxy. Don't expose `/metrics`
to the internet.

```nginx
location /metrics {
    allow 10.0.0.0/8;     # private Prometheus subnet
    deny  all;
    proxy_pass http://syrotp-server:3000/metrics;
}
```

Drop into your `prometheus.yml`:

```yaml
scrape_configs:
  - job_name: syrotp-server
    metrics_path: /metrics
    scrape_interval: 15s
    scrape_timeout: 10s
    static_configs:
      - targets: ["syrotp-server:3000"]
        labels:
          env: production
```

Verify the scrape:

```bash
curl -sf http://syrotp-server:3000/metrics | head -30
# # HELP syrotp_verifications_started_total ...
# syrotp_verifications_started_total{app_id="app_..."} 0
# ...
```

Full metric reference, label semantics, and recommended dashboards live
in [`monitoring.md`](monitoring.md).

## 2. Admin dashboard

SYROTP ships a read-only HTML dashboard at `/admin/*`, behind HTTP Basic
Auth. It is **disabled by default** — if `ADMIN_USER` or
`ADMIN_PASSWORD_HASH` is unset, every `/admin/*` request returns 404
and there is no auth surface to attack.

When enabled, the dashboard surfaces:

| Path | What it shows |
| --- | --- |
| `/admin`               | Overview cards: receivers, pending verifications, verified-24h, inbound-24h, unmatched-24h |
| `/admin/receivers`     | Receiver health, masked MSISDNs, heartbeat age, caps |
| `/admin/verifications` | Recent verifications (status, app, masked phone, age) |
| `/admin/inbound-sms`   | Inbound SMS — **length-only display**, the body itself is never rendered |
| `/admin/health`        | DB / Redis liveness + receiver counters |

Every `/admin` response carries the hardening headers `X-Frame-Options:
DENY`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`,
`Cache-Control: private, no-store`, and a strict CSP
(`default-src 'none'; …`) with no `script-src` allowance — the dashboard
is server-rendered HTML with no JS.

The dashboard never displays full E.164 phone numbers, verification
codes, full SMS bodies, API keys, gateway signing keys, or encryption
wrap blobs. Phones are masked to `+96399****` style, SMS bodies are
shown as `VERIFY *** (N bytes)`. These guarantees are pinned by 9
integration tests (`AD1`–`AD9`).

## 3. Configure admin auth

The dashboard reads two env vars at server startup:

| Var | Format | Notes |
| --- | --- | --- |
| `ADMIN_USER`            | UTF-8 string | The username for Basic Auth. |
| `ADMIN_PASSWORD_HASH`   | `scrypt$<saltHex>$<hashHex>` | Generated by the helper below. |

Generate a hash:

```bash
pnpm --filter @syrotp/server run admin:hash
# Password: ********
# Confirm:  ********
# scrypt$3f1a...$9c2d...
```

The helper takes a hidden password (no echo, no shell history), runs
scrypt with `N=16384 r=8 p=1 keylen=64`, and prints the storage form.
Copy the line into your `.env` (or secret manager):

```
ADMIN_USER=admin
ADMIN_PASSWORD_HASH=scrypt$3f1a...$9c2d...
```

Restart the server. `/admin/*` is now mounted; visiting it prompts for
HTTP Basic credentials.

**Hash format check.** The server validates the hash format on startup
and refuses to mount the dashboard if the regex doesn't match — a
truncated paste fails fast instead of silently disabling auth.

**Wrong password?** The server returns generic `401` whether the
username is wrong, the password is wrong, or both. There is no
username-existence oracle: both compares run with `timingSafeEqual`
before the decision. A correct user / wrong password and a wrong user /
wrong password produce identical timing.

**Rotation.** To change credentials: generate a new hash, swap
`ADMIN_PASSWORD_HASH`, restart. There is no in-place rotation API in
v0.3.

## 4. Android Gateway runbook

Use the Android gateway when you have a spare phone with a SIM on the
operator you want to receive on. See
[`apps/android-gateway/`](../apps/android-gateway/) for the source.

### Provision

On the SYROTP server host:

```bash
pnpm syrotp bootstrap \
  --app-name "android-gateway-1" \
  --msisdn "+963991234567"
```

That prints (once, never again):

- **Receiver ID** — `rcv_...`
- **Gateway signing key** — long hex value

### Build & install

```bash
cd apps/android-gateway
./gradlew :app:assembleDebug
adb install app/build/outputs/apk/debug/app-debug.apk
```

### Pair

1. Open **SYROTP Gateway** on the phone.
2. Enter:
   - Server URL: `https://otp.example.com` (no trailing slash; HTTPS
     required in production — cleartext is blocked by the network
     security config).
   - Receiver ID: `rcv_...`.
   - Signing key: paste the hex value from bootstrap. It's
     imported directly into AndroidKeyStore (not just encrypted at
     rest) so the raw bytes never live in app memory or in the data
     partition. See
     [`docs/android-gateway-keystore.md`](android-gateway-keystore.md)
     for threat model, migration, rotation, and compromise recovery.
3. Tap **Save & pair**. Grant SMS read permission when prompted.
4. Status switches to **Paired**, queue depth `0`.

### Operate

- **Disable battery optimization** for the app (Settings → Apps →
  SYROTP Gateway → Battery → Unrestricted), or Doze will pause uploads.
- **Multi-SIM** is reported per-inbound when the device exposes the slot
  via the standard SubscriptionManager APIs.
- **Local development** (emulator → host machine): edit
  `apps/android-gateway/app/src/main/res/xml/network_security_config.xml`
  to allow cleartext to `10.0.2.2`. Don't ship this config.

### Verify

From another phone, send `VERIFY ABCDEF` to the gateway's SIM number.
Within a few seconds:

- The gateway's queue depth ticks up, then back to 0.
- The SYROTP server's `syrotp_inbound_received_total{matched="false",reason="no_match"}`
  counter increments (no pending verification with code `ABCDEF` yet).

To verify a real verification: drive `pnpm syrotp smoke` against your
server with the gateway paired, then send the printed `VERIFY <code>`
from a separate phone whose number was passed as `SYROTP_PHONE`.

iOS cannot run a receiver — Apple does not allow programmatic SMS
reading. Use Android or the GSM modem path.

## 5. Python GSM Gateway runbook

Use the Python gateway when you'd rather have a Linux box + USB modem
(SIM800/SIM900 boards, Quectel/Huawei sticks) than a phone-shaped
device. Same wire protocol, same HMAC scheme, same admin surface.

Full install walkthrough: [`gsm-gateway.md`](gsm-gateway.md). Briefly:

```bash
sudo useradd --system --home /opt/syrotp-gateway --shell /usr/sbin/nologin syrotp-gateway
sudo usermod -a -G dialout syrotp-gateway

sudo python3 -m venv /opt/syrotp-gateway/venv
sudo /opt/syrotp-gateway/venv/bin/pip install /path/to/repo/apps/gsm-gateway

sudo install -d -m 750 -o syrotp-gateway -g syrotp-gateway /etc/syrotp-gateway
sudo install -m 600 -o syrotp-gateway -g syrotp-gateway \
  apps/gsm-gateway/config.example.toml /etc/syrotp-gateway/config.toml
sudoedit /etc/syrotp-gateway/config.toml          # paste real receiver values

sudo install -m 644 apps/gsm-gateway/systemd/syrotp-gateway.service \
  /etc/systemd/system/syrotp-gateway.service
sudo systemctl daemon-reload
sudo systemctl enable --now syrotp-gateway
journalctl -u syrotp-gateway -f
```

What you should see in the journal once provisioned:

```
INFO syrotp_gateway.modem: opening modem at /dev/ttyUSB0 @ 115200 baud
INFO syrotp_gateway.modem: modem initialized
INFO syrotp_gateway.service: reader: poll every 5.0s
INFO syrotp_gateway.service: heartbeat ok depth=0 signal=-77
```

The service `Restart=always`, persists pending uploads in a SQLite
queue at `/var/lib/syrotp-gateway/queue.db`, and pauses uploads (but
keeps queueing) on `401` so a wrong key doesn't DoS the server.

## 6. Smoke and loadtest after every deploy

Two checks belong in the post-deploy timeline of every release.

### Smoke (a few seconds)

```bash
export SYROTP_BASE_URL=https://otp.example.com
export SYROTP_PUBLIC_KEY=pk_live_...
export SYROTP_SECRET_KEY=sk_live_...
export SYROTP_RECEIVER_ID=rcv_...
export SYROTP_GATEWAY_KEY=...                   # 64-hex signing key
export SYROTP_PHONE=+963991234567
pnpm syrotp smoke
# [smoke] PASS  (216ms)
```

The smoke script signs a fake inbound itself — it's the "does the
protocol round-trip" check. Run it on every deploy; wire it as a
synthetic monitor that runs every few minutes and pages on failure.

### Loadtest quick (~5 seconds)

```bash
pnpm syrotp loadtest quick
# scenario-a: ✓ p95-start ≤ 400ms / success ≥ 99.9% / no 5xx
# replay-storm: ✓ no double-verifications under 50× burst
```

The quick gate is the CI gate. Run the full release baseline (all 5
scenarios, ~3 minutes) before tagging a release:

```bash
pnpm syrotp loadtest release-baseline
# writes tools/loadtest/reports/<timestamp>/summary.md
```

See [`performance.md`](performance.md) for reference numbers per
platform.

## 7. Alerts

The three alerts you should not ship without — copy verbatim into
your `alertmanager` rules:

```yaml
groups:
- name: syrotp
  rules:
  - alert: SyrotpReceiverStaleHeartbeat
    expr: syrotp_receiver_heartbeat_age_seconds > 300
    for: 2m
    annotations:
      summary: "Receiver {{ $labels.receiver_id }} hasn't heartbeat in 5+ minutes"
      runbook: "operations.md#8-runbook-receiver-stale-heartbeat"

  - alert: SyrotpInboundMatchRateDrop
    expr: |
      (
        sum(rate(syrotp_inbound_received_total{matched="true"}[5m]))
        /
        sum(rate(syrotp_inbound_received_total[5m]))
      ) < 0.5
    for: 10m
    annotations:
      summary: "Less than 50% of inbound SMS are matching pending verifications"
      runbook: "operations.md#9-runbook-high-inbound-unmatched-rate"

  - alert: SyrotpHmacRejectsSpike
    expr: sum(rate(syrotp_hmac_rejected_total[5m])) > 1
    for: 5m
    annotations:
      summary: "HMAC rejects > 1/s — gateway misconfiguration or attack"
      runbook: "operations.md#10-runbook-hmac-rejects-spike"
```

A clean SYROTP deployment sees zero `syrotp_hmac_rejected_total` activity
in steady state — every spike means either a gateway is misconfigured
or someone is probing the inbound endpoint.

Optional but recommended:

- `up{job="syrotp-server"} == 0` for at least 1 minute (server down).
- `histogram_quantile(0.95, sum(rate(syrotp_verification_start_duration_seconds_bucket[5m])) by (le)) > 0.5`
  for 10 minutes (start-verification p95 > 500 ms).

## 8. Runbook: receiver stale heartbeat

**Symptom.** `SyrotpReceiverStaleHeartbeat` is firing for one or more
receivers. The dashboard's `/admin/receivers` shows them as `stale`.

**What's actually wrong.** A gateway hasn't heartbeat in 5+ minutes.
Five typical causes, ordered by frequency:

1. **Gateway device is offline** — phone is dead / dropped Wi-Fi /
   modem unplugged.
2. **Network partition** between the gateway and the SYROTP server.
3. **Gateway clock drifted** more than `INBOUND_TIMESTAMP_SKEW_SECONDS`
   (default 300s) from the server. Heartbeats are signed with the
   gateway's clock; the server rejects requests outside the window.
4. **Wrong signing key** in the gateway config (recently rotated and
   the gateway wasn't updated).
5. **Server side**: the receiver was disabled in the admin DB and the
   gateway hasn't been told.

**Triage.**

```bash
# 1. Confirm the receiver and its expected MSISDN.
pnpm syrotp receiver list
# Look at last_heartbeat_at vs now.

# 2. From the gateway box, can it reach the server at all?
curl -sf https://otp.example.com/v1/health
# {"status":"ok",...}

# 3. From the gateway box, what's its clock?
date -u
# Compare with the server's date -u; > 5 min skew → fix NTP.

# 4. Watch the server's HMAC-reject reasons.
sum by (reason) (rate(syrotp_hmac_rejected_total{}[5m]))
# timestamp_skew  → fix gateway NTP
# bad_signature   → wrong signing key
# unknown_receiver → receiver was disabled, or wrong receiver id in config
```

**Fix.**

- Power-cycle the gateway phone or `systemctl restart syrotp-gateway`.
- Re-enable NTP if the clock is off.
- Re-pair the gateway if the signing key was rotated.
- If the receiver is intentionally retired, **delete the alert** rather
  than letting it page on a known-decommissioned device. A row in the
  admin UI with `enabled=false` is the right end state.

## 9. Runbook: high inbound unmatched rate

**Symptom.** `SyrotpInboundMatchRateDrop` is firing — fewer than 50% of
inbound SMS land on a pending verification. The dashboard's
`/admin/inbound-sms` shows lots of `unmatched` rows.

**What's actually wrong.** SMS are arriving at a receiver but the
matcher rejects them. The reason matters. Pull the breakdown:

```promql
sum by (reason) (rate(syrotp_inbound_received_total{matched="false"}[5m]))
```

Possible reasons:

| `reason`     | Likely cause | Fix |
| --- | --- | --- |
| `no_match`   | Sender ≠ verification's expected phone (most common: format/region differs), or code prefix typo, or no pending verification existed. | Check the receiver's region matches the senders' MSISDN format. Verify the SDK is normalizing to E.164 before calling `POST /v1/verifications`. |
| `expired`    | Pending row past TTL by the time the SMS arrived. | Bump `VERIFICATION_TTL_SECONDS` if your users routinely take longer than 10 min, or add a UI hint encouraging faster send. |
| `duplicate`  | Same `idempotency_key` for this receiver — the gateway re-uploaded an SMS it had already sent. | Expected on retries; only investigate if it's a large fraction. |

The dashboard at `/admin/inbound-sms` is read-only and length-only —
**you cannot read the SMS body** there to debug a specific case. That
is intentional. To investigate a single message, look at the audit log:

```sql
SELECT
  resource_id,
  action,
  meta,
  created_at
FROM audit_log
WHERE action LIKE 'inbound.%'
ORDER BY created_at DESC
LIMIT 50;
```

The `meta` column has the matcher's structured reason without quoting
any user content.

If the unmatched rate is *suddenly* very high, the most common root
causes are:

- A new SDK version that stopped normalizing phone numbers.
- A carrier that started prepending an extra digit / replaced `+` with `00`.
- A gateway whose modem clock drifted past the skew window — every
  inbound is being rejected before the matcher even sees it (would
  also light up `SyrotpHmacRejectsSpike`).

## 10. Runbook: HMAC rejects spike

**Symptom.** `SyrotpHmacRejectsSpike` is firing —
`syrotp_hmac_rejected_total` is incrementing at > 1/s.

**Why it matters.** A clean SYROTP deployment sees zero HMAC rejects in
steady state. Every spike is either a gateway misconfigured against
your server, or someone is probing the inbound endpoint without a
valid signing key. Both deserve eyes.

**Triage.** Group by reason:

```promql
sum by (reason) (rate(syrotp_hmac_rejected_total[5m]))
```

The `reason` enum maps directly to the verifier's return codes
([`hmac.ts`](../apps/server/src/services/hmac.ts)):

| `reason`              | Means | Likely cause |
| --- | --- | --- |
| `bad_receiver_id`     | Header `X-SYROTP-Receiver` doesn't match `^rcv_[A-Za-z0-9]+$`. | A non-SYROTP scanner / fuzzer probing. Block at the proxy. |
| `bad_nonce` / `bad_signature_format` | Headers don't match the expected hex shape. | Same — non-SYROTP traffic. |
| `bad_timestamp` / `timestamp_skew` | Clock outside the skew window (default 300s). | Gateway NTP broken. Fix on the gateway. |
| `unknown_receiver`    | Receiver row is disabled or doesn't exist. | Receiver was retired without retiring the gateway, or wrong receiver id in the config. |
| `key_unavailable`     | The wrap couldn't be decrypted with the master key. | `MASTER_ENCRYPTION_KEY` was rotated without re-wrapping receivers. **Stop and revert** — this is data-availability-critical. |
| `bad_signature`       | The signature doesn't match. | Wrong signing key in the gateway, or bytes were modified in transit. |
| `replay`              | Nonce was already used within the skew window. | A retry is hitting after the original made it — usually benign. A storm is suspicious. |

**Fix.**

- **Many `bad_signature` from one receiver** — that gateway has the
  wrong signing key. Re-bootstrap or re-pair.
- **Many `timestamp_skew`** — the gateway's clock is wrong. Fix NTP.
- **Many `bad_receiver_id` / `bad_nonce` from random IPs** — drop them
  at the WAF / reverse proxy. The endpoint is hardened (fast reject,
  per-receiver rate limit, generic 401) but log noise is still cost.
- **Any `key_unavailable`** — incident: master key rotation broke
  receiver decryption. Roll back the master key and follow the
  rotation procedure in [`SECURITY.md`](../SECURITY.md).

## Appendix: ops-relevant env vars

The full surface lives in [`.env.example`](../.env.example) and
[`config.ts`](../apps/server/src/config.ts). The ones that matter for
ops:

| Var | Default | Why ops cares |
| --- | --- | --- |
| `ADMIN_USER`                                | unset (admin disabled) | Username for `/admin`. Empty = no admin. |
| `ADMIN_PASSWORD_HASH`                       | unset (admin disabled) | scrypt hash for `/admin`. Empty = no admin. |
| `RECEIVER_HEARTBEAT_TIMEOUT_SECONDS`        | 120  | After this many seconds without a heartbeat, the receiver is `stale` on the dashboard and `syrotp_receiver_heartbeat_age_seconds` keeps climbing. Tune based on your gateways' heartbeat cadence. |
| `INBOUND_TIMESTAMP_SKEW_SECONDS`            | 300  | The HMAC verifier's clock window. Tighter is safer; looser tolerates worse NTP. |
| `VERIFICATION_TTL_SECONDS`                  | 600  | How long a pending verification stays valid. Match user expectations. |
| `MAX_PENDING_PER_PHONE`                     | 3    | Caps abuse from one phone. Bump only if you understand the abuse vector. |
| `RATE_LIMIT_*`                              | varies | Per-IP / per-receiver caps. The defaults in `.env.example` are production-realistic. The release-baseline `.env` loosens them — **don't ship those values**. |
| `TRUSTED_PROXIES`                           | empty | Comma-separated CIDR list of upstream proxies whose `X-Forwarded-For` is honoured (e.g. `10.0.0.0/8,127.0.0.1`). Leave empty to trust no upstream. |
| `TRUST_PROXY`                               | false | Legacy boolean. In production it MUST be paired with a non-empty `TRUSTED_PROXIES` or the server refuses to boot. |
| `CORS_ORIGINS`                              | empty | Empty = no cross-origin allowed. `*` is permitted but never recommended. |
| `LOG_LEVEL`                                 | info | `debug` only when actively investigating; the noise is significant. |

Restart the server after changing any of these — they're read once at
startup, not on every request.
